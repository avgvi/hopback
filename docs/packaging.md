# Packaging and releases

How hopback gets from this repository to each install channel. Every channel
installs both commands, `hopback` and `hb`.

Nothing here runs by itself. The release workflow starts only when a version
tag is pushed, and every push, tag and publish is the maintainer's decision.

## Channels

| Channel | User installs with | Built by | Config |
|---|---|---|---|
| GitHub Releases | `curl … hopback-installer.sh \| sh` | cargo-dist: archives per target, checksums, shell installer | `dist-workspace.toml`, `.github/workflows/release.yml` |
| Homebrew | `brew install avgvi/tap/hopback` | cargo-dist writes `hopback.rb` and pushes it to `avgvi/homebrew-tap` | `dist-workspace.toml` (`tap`, `publish-jobs`) |
| npm | `npm i -g hopback`, `npx hopback` | cargo-dist's npm installer package, which downloads the release binary | `dist-workspace.toml` |
| crates.io | `cargo install hopback`, `cargo binstall hopback` | `cargo publish`, by hand | `Cargo.toml` (`include`, metadata) |
| PyPI | `uv tool install hopback`, `pipx install hopback` | maturin with `bindings = "bin"`: wheels that carry the two binaries | `pyproject.toml` |
| Nix | `nix run github:avgvi/hopback` | the flake | `flake.nix`, `nix/package.nix` |
| mise | `mise use -g ubi:avgvi/hopback` | nothing extra: it reads the GitHub release archives | none |

Release targets: `aarch64-apple-darwin`, `x86_64-apple-darwin`,
`aarch64-unknown-linux-gnu`, `x86_64-unknown-linux-gnu`. Each archive holds
`hopback`, `hb`, `README.md`, `CHANGELOG.md`, `LICENSE`, and `hopback.1`.

## Build everything locally

None of these upload anything.

```bash
# Release archive for this machine, then the installers (shell, Homebrew, npm)
dist build
dist build --artifacts=global
ls target/distrib/

# What a release would contain, for every target
dist plan

# Python wheel carrying both binaries
uvx maturin build --release --out dist-wheels/

# crates.io package
cargo package --list
cargo package

# Nix, when Nix is installed
nix build
nix flake check
```

cargo-dist is pinned in `dist-workspace.toml` (`cargo-dist-version`). After
editing that file, run `dist generate` so `.github/workflows/release.yml`
matches; the workflow checks this and fails when it is stale.

## What the release workflow does

`.github/workflows/release.yml` is generated by cargo-dist. It runs **only on
a pushed tag that looks like a version** (`v0.2.0`); `pr-run-mode = "skip"`
keeps it off pull requests. On such a tag it:

1. plans the release from `Cargo.toml` and `dist-workspace.toml`;
2. builds the four archives and their checksums;
3. builds the shell installer, the Homebrew formula and the npm package;
4. creates the GitHub Release and uploads everything;
5. pushes `hopback.rb` to `avgvi/homebrew-tap` and publishes the npm package.

It needs two repository secrets, and the tap repository must exist first:

| Secret | For |
|---|---|
| `HOMEBREW_TAP_TOKEN` | A token that can push to `avgvi/homebrew-tap` |
| `NPM_TOKEN` | An npm token that can publish `hopback` |

crates.io and PyPI are not in the workflow. Publish them by hand after the
GitHub Release exists (`cargo binstall` and the wheels' users expect the same
version everywhere).

## Cutting a release

Each step that leaves this machine needs the maintainer's go-ahead.

1. Set the version in `Cargo.toml`, run `cargo build` so `Cargo.lock` follows,
   and regenerate the man page: `cargo run --bin hopback -- man > man/hopback.1`.
2. Move the Unreleased entries in `CHANGELOG.md` under the new version.
3. Run the checks and the local builds above.
4. Commit, tag `vX.Y.Z`, push the commit and the tag. The workflow does the
   GitHub Release, Homebrew and npm.
5. `cargo publish`.
6. Build wheels for every target and upload them to PyPI (`maturin build` per
   target or in CI, then `maturin upload`).

## Notes

- **Homebrew trust:** Homebrew refuses formulae from third-party taps until the
  user trusts them. Installing by the full name, `brew install
  avgvi/tap/hopback`, adds the tap and trusts that one formula in the same
  step (`Trust.trust_fully_qualified_items!` in `cmd/install.rb` of Homebrew
  7.0.13), so the README shows only that command. `brew install hopback`
  without the tap name would need `brew trust --formula avgvi/tap/hopback`
  first.
- **mise and GUI apps:** tools installed through mise's npm or Python backends
  are invisible to GUI apps unless mise's shims are on the login PATH. The
  `ubi:` backend, uv and Homebrew do not have that problem.
- **Names:** `hopback` must be reserved on crates.io, npm and PyPI before the
  first release; registries hand names out first come, first served.
